## 一、文件目的與使用方式

本文件集中管理使用者研究、Demo Persona、Current Journey、Pain Points 與待驗證假設。它不是虛構人物傳記，也不是需求的單一事實來源；Persona 的功能需求與驗收條件仍以 02 文件為準，交付順序仍以 03 Story Map 為準。

v0.2 只凍結會影響場域、語言、權限、UX、資料隔離與 Demo 的 Persona 骨架。詳細年齡、興趣、完整作息、歷史事件、對話稿與測試資料，應在使用者訪談、UX 原型及 Demo 腳本階段逐步補齊。

## 二、研究狀態與證據等級

目前 Persona 主要根據競賽命題、公開長照情境、團隊產品假設及既有使用者故事建立，尚未視為直接使用者研究結論。

證據等級：

• Confirmed：由命題、法規、公開來源或實測資料支持。

• Observed：由訪談、可用性測試或實際行為觀察支持。

• Assumed：團隊暫定假設，仍需驗證。

• Decided：基於交付範圍做出的產品決策，不等於市場事實。

Gate 1 前最低研究要求：

• 1 位機構照服員或長照相關工作者訪談。

• 1 位居家服務員／居服員或家屬訪談。

• 1 次長者端語音、同意與記憶確認原型測試。

• 更新 Current Journey、Pain Point Inventory 與 Assumption Register。

## 三、跨場域產品決策

Target Architecture 同時支援日照中心／社區關懷據點與居家服務。主要 Live Demo 採日照中心情境；居家服務用於證明派案、專業居服工作流、家屬報表與跨場域權限收斂。

機構照服員可依所屬 tenant 與授權關係管理同據點多位長者；居家服務員／居服員依派案與服務關係管理一位或多位長者；家屬透過專屬 App／Web 查看經同意且已發布的每日摘要、週報與月報。兩種專業照護場域與家屬端共用語音、事件、摘要、記憶、授權與報表資料基礎，不建立三套獨立產品。

角色與場域關係：

• 幸福日照中心：林阿嬤、張阿姨、機構照服員。

• 居家照護：陳伯伯、居家服務員／居服員、家屬。

• 林阿嬤為主端到端 Demo Persona。

• 張阿姨用於多長者概覽、不同狀態及資料隔離。

• 陳伯伯用於居服員派案／服務詳情、家屬報表中心與跨場域權限驗證。

## 四、Persona 設計原則

• 全部姓名、音檔、聯絡資訊與生活資料皆為模擬資料。

• Persona 不直接被標示為孤獨、憂鬱、失智或服藥不正常。

• 健康與用藥僅記錄長者陳述，不形成診斷或治療結論。

• 每位 Persona 有明確場域、語言、照護關係與 Demo 驗證目的。

• 同意狀態分項管理，不因同意一般對話就自動同意長期記憶、陪伴分析、主動陪伴或家屬通知。

• Persona 之間的事件、摘要、記憶、Graph 關係與檢索 Context 必須隔離。

## 六、Persona 1｜林阿嬤 v0.2

### 6.1 基本骨架

• 虛擬代稱：林阿嬤。

• 主要場域：平日白天至幸福日照中心活動。

• 主要語言：臺語，偶爾混用國語。

• 數位能力假設：不習慣打字及複雜選單，能理解明顯按鈕與短句語音提示。

• 照護關係：由日照中心照服員管理；女兒住外地，作為家屬通知接收者。

• 主要使用目標：用熟悉語言自然聊天，不需重複解釋已確認的重要生活關係。

### 6.2 主 Demo 情境

林阿嬤以臺語描述昨晚睡不好、早餐吃粥，並提到女兒最近沒有打電話。系統進行 ASR、低信心確認、安全回覆、事件擷取與候選記憶確認；「每週日等女兒電話」在她確認後才成為長期記憶，並於下一輪對話中被自然引用。照服員之後查看摘要、時間軸與來源證據並完成覆核。

### 6.3 初始同意設定

• 一般語音陪伴：同意。

• 生活事件擷取與每日摘要：同意。

• 長期記憶：初始同意，但每筆候選記憶仍需確認。

• 陪伴需求分析：待明確說明及測試後決定。

• 家屬通知：可同意，但實際送出前仍需照護者確認。

• 主動陪伴：獨立同意，v0.2 不預設開啟。

### 6.4 待驗證假設

• 能理解「要不要讓我記住這件事」的短句確認方式。

• 偏好一至兩句的簡短語音回覆。

• 對 AI 引用已確認家人聯繫習慣感到自然，而非被監控。

• 能清楚區分一般聊天、生活紀錄與長期記憶。

## 七、Persona 2｜張阿姨 v0.2

### 7.1 基本骨架

• 虛擬代稱：張阿姨。

• 主要場域：與林阿嬤同屬幸福日照中心。

• 主要語言：國語；客語路徑是否納入 Demo 待穩定度決定。

• 數位能力假設：可理解簡單文字提示，但仍以語音及大按鈕操作為主。

• 照護關係：由同一機構照服員管理。

• 主要使用目標：獲得日常陪伴並留下可追溯生活紀錄。

### 7.2 Demo 驗證目的

• 在多長者概覽中與林阿嬤同時出現。

• 顯示不同的最後互動時間、互動次數、摘要狀態與待覆核數量。

• 驗證沒有資料時顯示「未提及」或「資料不足」。

• 驗證林阿嬤的記憶、事件及 Graph 關係不會出現在張阿姨的頁面或對話 Context。

### 7.3 初始同意設定

• 一般語音陪伴：同意。

• 長期記憶：可設為尚未同意，用於驗證沒有長期記憶仍可使用基本陪伴。

• 家屬通知及主動陪伴：v0.2 不開啟。

### 7.4 待驗證假設

• 多長者概覽以摘要狀態及待覆核事件為主要資訊，對照服員最有幫助。

• 客語加分展示不應影響核心國語／臺語流程穩定度。

• 空狀態與資料不足狀態能被照服員快速理解。

## 八、Persona 3｜陳伯伯 v0.2

### 8.1 基本骨架

• 虛擬代稱：陳伯伯。

• 主要場域：居家照護。

• 主要語言：國語。

• 數位能力假設：主要使用語音；初始設定可由居服員或授權家屬協助，但兩者權限不同。

• 照護關係：由居家長照機構派案之居服員提供專業服務；家屬透過家屬端查看已發布摘要與報表。

• 主要使用目標：在家中完成低操作負擔的日常互動與生活紀錄。

### 8.2 Demo 驗證目的

• 居服員登入後查看今日服務行程或派案長者清單；由陳伯伯的行程卡進入其服務詳情。

• 居服員只能看到有效派案與授權範圍內的長者，不得看到林阿嬤與張阿姨。

• 家屬角色可在 App／Web 查看已發布的每日摘要、週報、月報與歷史重要事件，不具事件修正、記憶管理或專業待辦建立權限。

• 驗證日照與居家共用相同事件、摘要與記憶資料模型。

### 8.3 初始同意設定

• 一般語音陪伴與生活摘要：同意。

• 長期記憶：待逐筆確認。

• 家屬分享與報表：可設定為同意；App／Web 保存正式報表，LINE／Email 為通知通路，頻率與靜默時段由家屬設定。

• 陪伴需求分析及主動陪伴：預設關閉。

### 8.4 待驗證假設

• 居服員從單一服務行程或僅有一筆有效派案進入時，直接開啟長者詳情較容易使用。

• 居服員與日照照服員可共用大部分長者詳情元件，但首頁需分為派案／行程模式與同據點多長者模式。

• 家屬偏好在 App／Web 保存每日摘要並查看週報／月報，再由 LINE／Email 接收可設定頻率的通知。

## 九、Current Journey v0.2

日照主流程：

林阿嬤進入日照中心 → 完成同意或讀取既有同意 → 按大按鈕說話 → 系統辨識與回覆 → 產生事件與候選記憶 → 林阿嬤確認 → 產生每日摘要 → 照服員由多長者概覽選擇林阿嬤 → 查看詳情與時間軸 → 修正或覆核。

居家權限流程：

居服員登入 → 查看今日行程／派案長者 → 選擇陳伯伯 → 進入服務詳情、摘要與事件 → 無法查看未派案長者或幸福日照中心其他長者。

## 家屬報表流程：

## 系統產生每日摘要 → 通過分享同意與發布檢查 → 將正式報表保存於家屬端 App／Web → 依家屬設定透過 LINE／Email 發送簡短通知 → 家屬進入 App 查看每日摘要、週報、月報與歷史重要事件。通知失敗不影響 App 內報表可見性；撤回分享授權後停止新報表與通知。

## 十、Pain Point Inventory v0.2

• 長者不熟悉文字輸入、複雜選單及持續麥克風狀態。

• 臺語、混語、慢速或低音量語音可能造成辨識錯誤。

• 長者可能不理解資料用途、長期記憶與一般對話的差異。

• 照服員同時照顧多位長者，無法逐一閱讀完整逐字稿。

• 居家服務員／居服員與家屬需要不同的可見範圍與操作權限。

• AI 錯誤事件或記憶若未經確認，會持續影響摘要及後續對話。

• 無資料、資料不足、低信心及服務失敗必須有清楚且不責怪使用者的提示。

## 十一、Assumption Register v0.2

A-01｜長者能理解候選記憶確認。狀態：待原型測試。

A-02｜照服員首頁最需要摘要狀態、待覆核數量與最後互動時間。狀態：待照服員訪談。

A-03｜居服員從單一服務行程或僅有一筆有效派案進入時，適合直接開啟長者詳情。狀態：待操作測試。

A-04｜日照與居家可共用主要 Domain、事件、摘要與記憶流程。狀態：產品決策，待實作驗證。

A-05｜家屬偏好在 App／Web 查看每日、每週與每月報表，並以 LINE／Email 接收通知。狀態：待家屬訪談。

A-06｜長者願意接受低風險主動陪伴。狀態：待訪談，不納入目前預設。

A-07｜客語路徑可在不影響核心流程的前提下作為加分展示。狀態：待技術 Spike。

## 十二、訪談與原型測試計畫

照服員訪談重點：

• 每天如何掌握多位長者近況？

• 哪些資訊最容易遺漏或重複確認？

• 多長者首頁第一眼最需要哪些欄位？

• 哪些 AI 結果一定要人工確認？

居服員訪談重點：

• 希望多常收到摘要？

• 服務前最需要看到哪些資訊，服務後哪些內容需要覆核或交接？

• 居服員、日照照服員與家屬的資料範圍及操作權限應如何區分？

家屬訪談重點：

• 每日、每週與每月報表各希望看到哪些內容？

• LINE、Email 與 App 通知的頻率、時間與靜默偏好為何？

• 哪些生活資訊適合分享，哪些內容只應由專業照護人員查看？

• 家屬是否需要歷史報表、重要事件與聯絡照護單位入口？

長者端原型測試任務：

• 開始與結束錄音。

• 理解系統正在處理或聽不清楚的狀態。

• 完成一筆候選記憶的接受或拒絕。

• 撤回或拒絕家屬通知、主動陪伴等特定用途。

## 十三、版本與維護規則

• v0.2 是 Persona 骨架，不應被描述為已完成使用者驗證。

• 訪談或原型測試後，需更新證據等級、Pain Points 與 Assumption Register。

• 影響角色、場域、語言、權限或主要旅程的變更需同步更新 01、02 與 03 文件。

• Persona v1.0 應在主要 UX Flow 與 Wireframe 凍結前完成。

• Demo 前再補完整測試資料、事件、摘要、Graph 關係、音檔及對話腳本。
