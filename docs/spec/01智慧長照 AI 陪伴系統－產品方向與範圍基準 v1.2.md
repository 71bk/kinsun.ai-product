# 二、問題定義

## 2.1 Problem Statement

臺灣偏鄉、資源不足社區、獨居與居家／日照場域中的長者，可能因子女外出、照護人力有限、醫療與社會支持資源不均，而缺少持續且容易取得的生活陪伴與資訊傳遞管道。同時，部分長者主要使用臺語、客語或混語，且數位操作能力有限，現有以文字、複雜選單或標準國語為主的數位服務並不容易使用。

照護者或家屬則常面臨另一個問題：資訊散落在對話、口頭交接與個人記憶中，必須閱讀大量逐字稿或反覆詢問，才能掌握飲食、睡眠、活動、用藥陳述、社交互動與近期需要關心的變化。

## 2.2 產品要解決的核心問題

• 降低長者使用數位服務的操作與語言門檻。

• 讓 AI 陪伴具有情境感知與確認式記憶，而不是固定腳本。

• 將日常對話轉成可追溯、可修正的生活事件與每日摘要。

• 讓照護者在不閱讀完整逐字稿的情況下快速掌握近況。

• 以同意、權限、安全檢查與人工覆核限制 AI 的決策範圍。

• 縮短長者、照護者與家屬之間的資訊落差，但不取代真人關懷。

## 2.3 不處理的問題

• 不提供醫療診斷、治療建議、停藥、改藥或疾病機率判定。

• 不取代照護者、社工或醫療專業人員。

• 不宣稱為二十四小時跌倒或環境監控設備。

• 不在 Demo 使用真實長者個資。

• 不讓未經確認的推測直接成為長期記憶、家屬通知或正式照護行動。

# 三、產品願景與價值主張

## 3.1 Product Vision

打造一套語音優先、可確認記憶、可追溯且受控的智慧長照 AI 陪伴系統，讓長者能以熟悉語言自然互動，並把重要生活資訊安全地轉化為照護者可理解、可覆核與可採取行動的資訊。

## 3.2 核心價值主張

對長者：

• 不必打字或理解複雜介面，即可用熟悉語言互動。

• AI 只引用已確認的個人資訊，避免錯誤記憶與過度推測。

• 聽不清楚或資料不足時會詢問與降級，而不是假裝理解。

對日照照服員與居家服務員：

• 以摘要、時間軸、證據句與待確認事項掌握近況。

• 可修正 AI 擷取結果，並保留版本與稽核紀錄。

• AI 只提供候選行動，正式待辦與通知仍由人員確認。

對家屬：

• 在取得授權後收到適量近況，不必閱讀完整逐字稿。

• 通知內容使用關懷語氣，避免診斷式或造成恐慌的描述。

對機構與偏鄉場域：

• 以可模組化的 AWS 架構支援不同語言、不同照護角色與逐步擴充。

• 透過資料治理、權限隔離與可觀測性建立可落地的技術基礎。

# 四、目標使用者與核心情境

## 4.1 主要使用者

長者：

偏鄉、獨居、居家照護、日照中心或社區關懷據點中的長者；可能偏好國語、臺語、客語、原住民族語、英文或混語，且數位操作能力有限。

機構照服員：

同時照顧多位長者，需要多長者概覽、每日摘要、待覆核事件與關懷待辦。

居家服務員／居服員：

由居家長照機構派案，到不同長者家中提供專業服務；可能同時負責多位被派案長者，需要今日服務清單、派案長者列表、服務前摘要、事件、記憶與後續追蹤。

## 4.2 次要使用者

家屬：

在取得授權後，透過家屬端 App／Web 查看已發布的每日摘要、每週／每月報表與歷史重要事件，並可設定 LINE／Email 通知；不直接修正事件、記憶或建立專業照護待辦。

內容管理者／系統管理者：

管理衛教來源、版本、量表、規則、權限、資料保留、模型與系統監控。

## 4.3 核心使用情境

• 長者以臺語或國臺混語描述昨晚睡眠、早餐與家人聯繫情況。

• 系統完成 ASR、情境回覆、事件擷取與候選記憶確認。

• 已確認記憶寫入正式資料，並在下一次對話中被正確引用。

• 系統根據當日事件產生可追溯摘要。

• 照護者查看時間軸、來源句與摘要，並修正錯誤。

• 經同意與必要覆核後，系統先將家屬版每日摘要保存並發布至家屬端，再依偏好透過 LINE／Email 發送簡短通知與安全連結。

• 在後續 Wave 中加入可信 RAG、陪伴需求訊號、主動陪伴、遊戲與多語擴充。

# 4.5 專業居服與家屬端產品決策

# 居家照護中的主要專業角色為居家服務員／居服員，不以家庭成員代稱。居服員可能同時負責多位派案長者，首頁以今日行程、派案長者、上次服務摘要與待追蹤事項為主；從特定派案或服務行程進入時，可直接開啟該長者詳情。

# 家屬端採專屬但輕量的 App／Web 報表中心。正式資料先保存於系統並以 report_id、版本與發布狀態管理；家屬可查看已發布的每日摘要、每週／每月報表、歷史重要事件與通知設定。LINE／Email 只作為通知與導流通路，不是正式資料保存來源。

# 日照照服員、居服員與家屬共用同一身份、授權、資料與 API 基礎，但依角色、tenant、派案與分享同意顯示不同首頁及功能。家屬不得查看完整逐字稿、未覆核事件、照護內部筆記、AI 技術資料或其他長者資訊。

# 五、證據、事實與待驗證假設

## 5.1 已確認事實

• 競賽命題要求完成語音互動陪伴、生活記錄與智慧摘要、照護者資訊介面。

• 系統不得作為醫療診斷或治療依據。

• 團隊已建立使用者故事 v1.3.1、Implementation Waves 與第一條 Vertical Slice。

## 5.2 外部與市場證據

• 命題文件指出城鄉長照、醫療與社會支持資源存在落差。

• 部分長者使用臺語或族語，且數位識能有限。

• 家庭照護者與機構人員需同時處理多位長者資訊，資訊傳遞效率不足。

• 現有公開長照法規與衛教來源可作為 RAG 與產品邊界依據。

## 5.3 尚待直接使用者驗證的假設

• 長者願意讓 AI 主動發起低風險陪伴。

• 長者能理解並願意操作「候選記憶確認」。

• 照護者最需要的是摘要、時間軸與待辦，而不是其他資訊排列。

• 家屬偏好固定頻率摘要，而不是事件即時通知。

• 長者對語音回覆長度、稱呼與主動互動頻率的偏好可被簡單設定。

• 日照場域與居家場域可以共用大部分產品流程。

## 5.4 使用者研究最低要求

在 Gate 1 正式簽核前，至少完成：

• 1 位照服員或照護相關工作者訪談。

• 1 位家庭照護者或家屬訪談。

• 1 次長者端語音／同意原型可用性測試；若無法接觸長者，需記錄限制並以代理使用者測試暫代。

• 一份 Current Journey、Pain Point Inventory 與 Assumption Register 更新。

# 六、產品目標與成功指標

## 6.1 產品成果指標

• 語音互動任務完成率：目標值需在原型測試後凍結。

• 候選記憶確認流程完成率：目標值需在原型測試後凍結。

## 6.2 系統與 AI 指標

• 固定 Demo Vertical Slice 可重複完整跑通。

• ASR 報告包含 CER、WER、Key-slot Accuracy、Negation Accuracy、關鍵事件保留率與 final latency。

• RAG 評估至少包含 Recall@K、MRR 或 NDCG@K。

• Agent Golden Dataset 涵蓋正常、資料不足、跨使用者隔離、Prompt Injection、醫療紅線、拒絕主動互動與 Graph 衝突。

## 6.3 Guardrail 指標

• 跨長者或跨 tenant 資料洩漏：0 件。

• 固定醫療紅線測試中的高風險違規輸出：0 件。

• 未經同意建立長期記憶、陪伴分析或家屬通知：0 件。

• 未確認推測寫入正式 Graph 或記憶：0 件。

• Demo 使用真實長者個資：0 件。

## 6.4 暫定工程門檻

• 語音結束至 ASR final：P95 目標不高於 2.5 秒。

• Agent 首段可播放內容：P95 目標不高於 5 秒。

• TTS 首段音訊：P95 目標不高於 2 秒。

• 語音結束至首段播放：P95 目標不高於 8 秒。

• 照護者主要頁面在 Demo 資料量下：P95 目標不高於 3 秒。

以上均為暫定工程目標，必須由 Spike 與實測更新，不得描述為已達成結果。

## 6.5 Stop／Pivot Criteria

符合下列任一條件時，團隊應縮減範圍或改用降級方案：

• 核心 A／B／C 端到端流程無法在 Demo 前穩定重跑。

• 臺語 ASR 無法可靠保留人物、否定、日期或用藥等關鍵資訊，且低信心確認仍無法補救。

• Graph DB 導入明顯阻塞核心流程時，改用 RDS 關係表或 Mock 投影保留設計證據。

• 主動陪伴、陪伴需求或遊戲影響核心 Demo 穩定度時，退回技術證據頁或延後 Wave。

• 任何功能無法滿足同意、權限、可追溯或醫療安全底線時，不得進入 Demo 主流程。

# 七、Scope 與交付邊界

## 7.1 完整 Target Architecture

完整產品規劃納入：

• 中／臺／客／英語音路徑與共用 Agent。

• 受控 Multi-Agent 與 Safety Evaluator。

• 確認式長期記憶。

• RDS 交易事實與 Graph 關係投影。

• 生活事件、每日摘要、時間軸與照護者覆核。

• 家屬每日摘要、每週／每月報表中心、LINE／Email 通知、可信 RAG、陪伴需求訊號與主動陪伴。

• 遊戲、積分、低資源語言與 ASR 適應。

## 7.2 Implementation Waves

Wave 1：核心語音、事件、確認式記憶、Graph 再次引用與安全基礎。

Wave 2：每日摘要、詳情、時間軸、人工覆核與待辦。

Wave 3：RAG、陪伴需求、家屬報表中心、LINE／Email 通知、主動陪伴與英文穩定路徑。

Wave 4：遊戲、積分、本土低資源語言、ASR 適應與持續改善。

## 7.3 第一條 Demo Vertical Slice

第一條 Demo 必須以同一位虛擬長者完整跑通：

同意 → 語音 → ASR → Orchestrator → 安全回覆 → 事件與候選記憶 → 長者確認 → RDS／Outbox → Graph 投影 → 下一輪引用 → 每日摘要 → 照護者詳情、時間軸與修正 → 技術證據。

## 7.4 明確延後或不納入目前交付

• 複雜 Multi-Agent 自由協商、辯論與無上限遞迴。

• 超過兩層且沒有明確查詢模式的 Graph 多跳推理。

• 從零訓練語言或語音模型。

• 模型並行與複雜分散式訓練。

• 完整 Learning to Rank 訓練。

• 年度生活報表與長期趨勢預測。

• 以自由對話取代正式量表。

• 公開競爭型健康排行榜。

• 與醫院 HIS／EMR 的正式生產整合。

• 真實緊急救援、二十四小時監控與自動修改照護計畫。

# 八、風險登錄

R1｜臺語／混語 ASR 不穩定

機率：高｜影響：高

緩解：固定測試集、低信心確認、關鍵欄位驗證、備援音檔、基底模型與微調模型比較。

Owner：語音負責人（待指定）

R2｜五人團隊範圍過大

機率：高｜影響：高

緩解：第一條 Vertical Slice 優先；每個 Wave 設 Gate；非核心功能使用 Feature Flag、Mock 或延後。

Owner：產品／技術負責人（待指定）

R3｜RDS 與 Graph 資料不一致

機率：中｜影響：高

緩解：Transactional Outbox、idempotency_key、重試、DLQ、重放與一致性測試；禁止無保護雙寫。

Owner：資料／後端負責人（待指定）

R4｜AI 產生醫療越界或無根據資訊

機率：中｜影響：高

緩解：Safety Evaluator、固定醫療紅線、Schema 驗證、最多一次修正、安全降級、Golden Dataset。

Owner：Agent／安全負責人（待指定）

R5｜同意、權限或刪除流程不完整

機率：中｜影響：高

緩解：Consent 狀態機、elder_id／tenant_id 隔離、刪除傳播測試、敏感日誌最小化。

R6｜RAG 來源不可靠或版本失效
