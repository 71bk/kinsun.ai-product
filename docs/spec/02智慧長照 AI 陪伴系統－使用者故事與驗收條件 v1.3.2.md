## 2026-08-14 Post-v1.3.2 Acceptance Overlay

本版既有 User Stories 繼續有效，但涉及帳號、角色、長者建立、場域切換與離場時，以下條件依 [ADR 0013](../adr/0013-separate-account-elder-enrollment-entitlement.md)／[Spec 17](17智慧長照%20AI%20陪伴系統－Account、Elder、Enrollment%20與%20Service%20Entitlement%20v0.1.md) 優先：

1. Organization Admin 建立 Elder Profile 時不得要求 Email、密碼或 OAuth，也不得自動建立 Actor。
2. Staff／Family 只能從 Server 授權清單選擇 Elder；知道或修改 `elder_id` 不得取得存取權。
3. Staff／Family 代啟動 Session 必須分別記錄 initiating actor 與 `elder_id`，不可冒充 Elder 登入。
4. Elder 離開機構後，該 Enrollment、Assignment、Staff access、未開始 Session 與自動排程必須終止，但 Elder／Account／既有資料不得被連帶刪除。

6. Elder 日後自行註冊時，必須 link 到既有 Elder，而不是建立第二份 Elder Profile。

本系統僅提供生活陪伴、照護溝通與健康資訊參考，不提供醫療診斷、治療建議，也不取代照護者、社工或醫療專業人員的判斷。

# 一、核心使用者

***長者（主要使用者）***

偏鄉、獨居、居家照護或日照場域中的長者，可能習慣國語、臺語、客語、原住民族語或國臺混語，數位操作能力有限，希望主要透過語音完成互動。

語言支援層級：國語與臺語為核心語音路徑；客語與原住民族語為加分語言（BONUS IF STABLE，對應命題加分項）；英語正式納入 Target Architecture 與 Implementation Wave 3，使用成熟 ASR／TTS 服務並與其他語言共用 Agent，不另訓練英文模型，也不建立英文 Agent。

Demo 落點：US-A01 至 US-A07、US-L01、US-L02。

2A. 機構照服員（主要使用者）

日照中心或社區關懷據點人員，同時照顧多位長者，需要在單一頁面快速掌握多位長者的生活近況、社交事件、陪伴需求訊號、摘要與待確認事項，但不能被大量逐字稿淹沒。權限範圍涵蓋所屬據點內的多位長者。

Demo 落點：US-C01、US-C02、US-C04、US-K03。

2B. 居家服務員／居服員（主要使用者）

由居家長照機構派案，到不同長者家中提供專業服務。居服員可能同時負責多位被派案長者，需要今日服務行程、派案長者列表、上次服務摘要、事件覆核與待追蹤事項；只能查看有效派案與授權範圍內的資料。

Demo 落點：US-C01、US-C02、US-C04（居服派案／服務詳情與權限證據）。

***家屬（次要使用者，但需在 Demo 出現）***

不一定能每日陪伴長者，希望在取得授權後，透過家屬端 App／Web 查看已發布的每日摘要、每週／每月報表與歷史重要事件，並依偏好接收 LINE／Email 通知。家屬不執行專業照護工作、不修正事件或記憶、不建立專業待辦。

Demo 落點：US-C03、US-C05（家屬報表中心與 LINE／Email 推播）。

***內容管理者／系統管理者（支援角色）***

負責衛教文件、量表與規則版本、題庫、權限、模型版本、資料保留、稽核與系統監控。此角色不出現在長者端主旅程，但必須在 Demo 的技術證據頁呈現至少一個實際後台畫面（來源登錄或版本管理），以支撐可追溯性主張。

Demo 落點：TE-G01 至 TE-G04、US-L04、NFR-H01、TE-J04。

# 二、產品原則

***語音優先：長者不需打字，也不需理解複雜選單。***

***人機協作：AI 協助整理證據與提出候選行動，不取代照護決策。***

***確認後記憶：可能影響未來互動的個人資訊，經確認後才成為長期記憶。***

***可追溯：摘要、關懷訊號、衛教回答與待辦應能回到來源事件或可信文件。***

***個人基準：互動變化以同一位長者的歷史資料為主，不用長者彼此比較。***

***最小必要資料：只蒐集完成服務所需資料，並提供更正、撤回及刪除方式。***

***非診斷定位：不得將互動變化直接標示為孤獨、憂鬱或其他疾病。***

***安全優先：不提供診斷、停藥、改藥或治療決策。***

# 三、優先順序與實作波次定義

Product Priority 用來表示完整產品的重要性；Implementation Wave 用來表示五人團隊的交付順序。兩者不得混用：MUST SHIP 不代表所有項目同時開工，Wave 4 也不代表能力不在完整產品架構中。

**Product Priority**

***MUST SHIP：完整產品與黑客松端到端 Demo 的必要能力。***

***COMMITTED INNOVATION：已納入 Target Architecture，形成產品辨識度的主要創新。***

***BONUS IF STABLE：核心穩定後交付，不得破壞主流程。***

***DEFERRED：明確不納入目前 Target Architecture 或需等待研究、授權與場域驗證。***

**Implementation Waves**

***Wave 1｜核心記憶垂直切片：長者語音 → ASR → Orchestrator → 事件擷取 → 候選記憶確認 → RDS＋Graph DB → 下次對話再次引用。***

***Wave 2｜照護者閉環：每日摘要、長者詳情、事件時間軸、人工覆核、關懷待辦與權限收斂。***

Wave 3｜關懷與可信服務：陪伴需求訊號、家屬報表中心、LINE／Email 通知、RAG、安全檢查、主動式個人化陪伴及英文穩定語音路徑。

***Wave 4｜擴充與優化：互動遊戲、積分、本土低資源語言加分、ASR 適應、進階評估、管理後台與推薦學習。***

# EPIC A｜長者語音互動陪伴

## US-A01｜低操作負擔的語音入口

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 1**

身為長者，我希望用一個明顯的大按鈕就能開始說話，讓我不必打字或操作複雜介面。

**驗收條件：**

***首頁可在一個主要操作內開始錄音。***

***錄音、處理、播放與錯誤狀態都有清楚的視覺及語音提示。***

***未授權麥克風時，以白話引導使用者完成授權。***

***行動裝置與桌面瀏覽器皆能完成基本流程。***

***麥克風不持續常駐開啟，錄音開始與結束狀態必須清楚可辨識。***

## US-A02｜國語與臺語語音辨識

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 1**

身為習慣國語、臺語或國臺混語的長者，我希望系統聽得懂我的說法，讓我不必刻意改用標準國語。

**驗收條件：**

***系統可依語言偏好或自動判斷選擇適當 ASR 路徑。***

***Demo 測試集至少涵蓋國語、臺語及一組國臺混語。***

***辨識信心不足時，不得假裝理解，應請長者重說或確認關鍵內容。***

***逐字稿保留模型版本、辨識時間與 ASR 信心。***

***客語與原住民族語列為 BONUS IF STABLE；英語由 Speech Router 依語言偏好切換至成熟的 en-US ASR／TTS 路徑，並與其他語言共用同一組 Agent。***

***進入英文模式後，Session 預設固定 en-US，直到長者明確要求切換；不應每句重新偵測。***

***英文路徑不需要另外微調模型，至少以 30 至 50 句臺灣口音英文與中英混語測試語料驗證。***

## US-A03｜符合語言偏好的語音回覆

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 1**

身為長者，我希望 AI 用我熟悉的語言、稱呼與回覆長度回應，讓對話自然且容易理解。

**驗收條件：**

***Persona 可設定主要語言、稱呼方式及預設回覆長度。***

***回覆預設不超過三個重點，避免過長語音造成理解負擔。***

***TTS 失敗時仍顯示文字回覆，並提供重新播放或稍後重試。***

***系統不得因語言轉換而改變用藥、日期、數量等關鍵資訊。***

## US-A04｜情境感知對話

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 1**

身為長者，我希望 AI 能理解現在的時間、近期事件與我已確認的偏好，讓它不像固定腳本。

**驗收條件：**

***每輪只注入與當前問題相關的時間、情境、近期摘要及已確認記憶。***

***未確認的候選記憶及陪伴需求推估不得當成事實使用。***

***無資料時不得虛構家人行程、健康狀況或過往對話。***

***每輪最多帶入預先設定數量的相關記憶，避免過度引用。***

## US-A05｜對話失敗的安全降級

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 1**

身為長者，我希望系統聽不清楚或服務暫時失敗時仍能簡單引導我，避免我以為自己操作錯誤。

**驗收條件：**

***ASR、LLM 或 TTS 逾時時提供簡短且可重試的提示。***

***同一輪最多自動重試一次，不得無限循環。***

***系統無法取得可信資料時，明確說明目前不知道或暫時無法回答。***

***失敗事件留下 trace ID，但日誌不得保存不必要的完整敏感逐字稿。***

## US-A06｜分層同意與資料用途控制

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 1**

身為長者，我希望知道系統會保存與分析什麼，並能分別決定是否同意。

**驗收條件：**

***第一次使用前以白話說明錄音、逐字稿、生活事件、長期記憶、陪伴需求分析、家屬通知及資料保存期限。***

***使用者可分別同意或拒絕長期記憶、陪伴需求分析與家屬通知。***

***長者可使用基本語音陪伴，但選擇不建立長期記憶或不進行陪伴需求分析。***

***同意狀態可撤回，撤回後不得再進行對應用途的新增分析。***

***刪除請求需處理原始資料及其衍生事件、摘要、記憶、訊號與索引。***

## US-A07｜週期生活回顧

**Product Priority：COMMITTED INNOVATION　｜　Implementation Wave：Wave 2**

身為長者，我希望用語音詢問最近一週的生活情況，了解自己的睡眠、飲食、活動與社交紀錄。

**驗收條件：**

***長者可用生活化語句查詢最近七日紀錄。***

***結果同時提供文字及語音。***

***沒有紀錄的日期明確標示「沒有資料」或「未提及」。***

***回顧只使用已記錄或已確認資料，不自行推測。***

***年度生活報表與長期趨勢預測列為 DEFERRED，避免與本版延後範圍矛盾。***

# EPIC B｜生活記錄與每日摘要

## US-B01｜自動擷取結構化生活與社交事件

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 1**

身為照護者，我希望系統自動從對話中擷取飲食、活動、睡眠、用藥陳述、情緒表達與社交事件，減少人工抄寫。

**驗收條件：**

***事件輸出通過固定 Schema 驗證後才能寫入正式資料庫。***

***用藥欄位只記錄「長者陳述」，不得推論服藥是否正確。***

***社交事件至少包含聯繫、預期聯繫未發生、活動參與、活動取消及明確陪伴需求表達。***

***每筆事件保存 event_time、recorded_at、event_type、evidence_text、asr_confidence、extraction_confidence、review_status 與來源識別。***

***不確定內容標記 needs_review，不得自動標記 verified。***

## US-B02｜每日 AI 摘要

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 2**

身為照護者，我希望每天看到一份精簡且可追溯的生活摘要，快速掌握長者近況。

**驗收條件：**

***摘要涵蓋飲食、活動、睡眠、用藥陳述、社交互動及重要事件。***

***沒有資料的欄位明確標示「未提及」。***

***每個摘要重點至少可回查一筆 event_id 與證據片段。***

***摘要不得新增原始資料中不存在的診斷或結論。***

***週期互動變化分析與一般每日摘要分開呈現。***

## US-B03｜照護者修正與覆核

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 2**

身為照護者，我希望修正 AI 擷取錯誤，讓後續摘要、記憶與陪伴需求分析更可靠。

**驗收條件：**

***後台可編輯事件內容、事件類型、事件時間及 review_status。***

***可標記 ASR 聽錯、事件誤判、裝置故障、外出或其他排除原因。***

***系統保存修正前後值、修正者及時間。***

***事件修正後，受影響摘要與陪伴需求訊號標記為需要重新計算。***

***修正資料可用於離線評估，但不得未經授權直接用於模型訓練。***

## US-B04｜事件時間軸

**Product Priority：COMMITTED INNOVATION　｜　Implementation Wave：Wave 2**

身為照護者，我希望按時間查看長者的重要互動與生活事件，快速理解變化。

**驗收條件：**

***可依日期、事件類型、來源及審查狀態篩選。***

***同一事件不因重新摘要而重複顯示。***

***時間軸可連回來源片段、每日摘要及照護者修正紀錄。***

***可匯出生活紀錄摘要供照護溝通參考，但不得標示為醫療診斷資料。***

# EPIC C｜照護者與家屬介面

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 2**

身為專業照護人員，我希望依工作場域看到同據點長者或被派案長者的摘要、行程與待處理事項，降低切換與交接成本。

# NON-FUNCTIONAL REQUIREMENTS Q｜暫定可量測門檻

以下為 v1.3.2 的暫定工程基準；未完成技術 Spike 的數值需以實測更新並保留 ADR。不得把暫定目標寫成已達成結果。

## NFR-Q01｜語音與頁面效能

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 1**

***語音結束至 ASR final：P95 不高於 2.5 秒；ASR timeout 5 秒。***

***Agent 產生首段可播放內容：P95 不高於 5 秒；LLM timeout 10 秒。***

***TTS 請求至首段音訊：P95 不高於 2 秒；TTS timeout 5 秒。***

***語音結束至首段回覆播放：P95 目標不高於 8 秒；超過門檻先播放處理中提示。***

***照護者主要頁面：Demo 資料量下 P95 載入不高於 3 秒。***

## NFR-Q02｜Context、Agent 與 Graph 限制

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 1**

***每輪最多帶入 8 筆已確認記憶與 12 筆近期事件；超出時依相關性與新鮮度截斷。***

***同一輪最多三個同步 Agent 步驟，超出部分改為非同步，不建立無上限遞迴。***

***Demo Graph 查詢最大 traversal depth 為 2，P95 目標不高於 500 毫秒。***

***所有跨服務請求具 trace_id；關鍵寫入具 idempotency_key。***

## NFR-Q03｜背景工作、通知與刪除

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 2–3**

***每日摘要在排程後 15 分鐘內完成；失敗最多重試三次，之後進入 dead-letter queue 並告警。***

***家屬通知最多重送三次，使用退避策略；仍失敗時顯示人工處理狀態，不得重複發送成功訊息。***

***撤回同意後立即停止新增分析；前台與檢索層在 24 小時內不可再取用待刪除資料。***

***正式環境完整刪除期限、備份保留與法遵處理在上線前由 Policy 與法律審查凍結。***

## 家屬報表發布成功後，即使 LINE／Email 通知失敗，App／Web 仍可查看；通知重試不得重複建立 report_id。

## 每次 LINE／Email 發送需保存 channel、status、sent_at、opened_at、retry_count 與錯誤原因。

## NFR-Q04｜評估資料最低門檻

**Product Priority：MUST SHIP　｜　Implementation Wave：Wave 1**

***Demo 固定測試至少包含 3 位虛擬 Persona、每種核心語言 30 句、正常／噪音／混語／否定／日期人物事件案例。***

***ASR 報告至少包含 CER、WER、Key-slot Accuracy、Negation Accuracy、關鍵事件保留率及 final latency。***

***RAG 以人工標註查詢集報告 Recall@K、MRR 或 NDCG@K；不使用未實測數字。***

***Agent Golden Dataset 至少覆蓋正常、資料不足、跨使用者隔離、Prompt Injection、醫療紅線、拒絕主動互動及 Graph 衝突案例。***

# 八、Demo 必演使用者旅程

主要 Demo Persona：林阿嬤。張阿姨提供日照多長者概覽；陳伯伯提供居服派案、家屬報表與跨場域資料隔離證據。

***林阿嬤以臺語說明昨晚沒睡好、早餐吃粥，並提到女兒最近沒有打電話。***

***ASR 顯示逐字稿；若關鍵詞信心不足，系統請她確認。***

***AI 依語言偏好、時間及已確認記憶安全回覆，不做醫療判斷。***

***系統建立睡眠、飲食與社交聯繫事件，附 evidence_text 與信心。***

***林阿嬤提到每個星期日會等女兒電話，系統詢問是否保存為長期記憶；確認後由 RDS 交易寫入，並透過 Outbox 建立 Graph 關係投影。***

***下一次互動以兩層 Graph 查詢找到「林阿嬤 → 女兒 → 每週日通話」關係，Companion Agent 可引用已確認事實；找不到或衝突時不得補造。***

***背景 Care Insight Agent 比較最近七天與過去二十八天，顯示「近期出現值得關心的變化」，並列出證據，不顯示孤獨分數。***

***照護者開啟詳情頁，查看來源句、資料完整度與排除原因。***

***照護者確認後建立「聯繫林阿嬤」及「三日後追蹤」待辦。***

照護者確認分享內容後，系統先將每日摘要發布至家屬端 App／Web，再透過 LINE 或 Email 實際送出通知；家屬可進入報表中心查看每日摘要與週／月報表（不含逐字稿、不含陪伴需求分數）。

***長者完成三題臺語互動小遊戲並取得參與積分。***

***內容管理者後台展示一份衛教文件的來源登錄、版本與審查狀態，並示範失效版本不會被檢索。***

***現場另以技術證據頁展示 ASR 評估、英文語音切換、可信來源回答、Graph 查詢、安全測試及受控 Agent trace。***

***在取得主動陪伴同意與照護者核准後，系統於允許時段以已確認記憶動態發起一次低風險關懷；長者可說停止或換題。***

# 九、Definition of Done

一個使用者故事只有在以下條件都成立時才算完成：

***功能已部署至可 Demo 的環境。***

***正常流程、失敗流程及權限流程均有測試。***

***使用者可觀察的驗收條件全部通過。***

***輸入、輸出、資料狀態及儲存位置寫入 README 或技術文件。***

***不使用真實長者個資。***

***不宣稱未實測的準確率、改善幅度、孤獨程度或醫療能力。***

***重要輸出可追溯至事件、來源、模型、Prompt、Policy、Graph 關係或規則版本。***

***Orchestrator 與專責 Agent 無法繞過同意、權限、Eligibility、Schema、安全檢查與人工核准。***

***RDS 與 Graph DB 的新增、更正、停用及刪除同步具備冪等、重試、補償與重放測試。***

***長者可撤回同意，並有資料更正及刪除流程。***

主 Demo 可由長者端完整走到專業照護端；家屬報表與通知流程另有可重跑的授權、發布與權限測試。
